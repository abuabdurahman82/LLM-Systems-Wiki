# The 20% of RAG Knowledge That Explains 80% of Production Quality

`LAST_UPDATED: 2026-08-29` · Status: core page · Synthesis page: [E] numbers come from the
machine-verified constants bank (2026-08-29); paper-level claims are tagged [I]/UNVERIFIED
because the consolidated research bank was not yet written at authoring time.

## 30-Second Explanation
Most production RAG failures are not model failures — they are retrieval and
context failures that the model then faithfully reports, or confidently hallucinates
around [I]. The fifteen principles below are the recurring root causes: what actually
limits answer quality, which pipeline stages are genuinely separate design decisions,
and where cost, security, and evaluation bite. A team that internalizes this page and
the baseline pipeline (03) will outperform a team that deployed agents and graphs on
top of a retriever nobody measured.

## Where quality is decided

```
            corpus ──► chunk ──► embed ──► index          (determines the ceiling)
                                            │
   query ──► understand ──► search ──► rerank ──► pack ──► LLM     (realizes it)
                                            │
                            measure BOTH layers ──► iterate the worse one
        ~80% of observed answer failures trace back to the left half [I]
```

## The fifteen principles

### 1. Retrieval quality limits generation quality.
A generator can only use evidence the retriever surfaced; if the supporting chunk
never enters the context, no prompt engineering recovers it [I]. Generation over good
evidence can still fail (faithfulness), but generation over absent evidence fails by
construction. That is why the first metric in any system is retrieval recall, not
answer fluency (45).
**How to check:** On a golden set (46), measure whether the evidence chunk appears in
top-k (recall@k) before you look at any answer-quality number.

### 2. Chunking is a retrieval design decision.
The chunk is the smallest unit your index can surface, so chunk boundaries define
what evidence can and cannot be retrieved atomically (10). Split mid-argument and the
retriever returns fragments; fuse whole sections and embedding specificity dilutes.
Size, overlap, and structure-awareness are trade-offs to measure, not defaults to copy.
**How to check:** Sample ten chunks for one real query type and ask whether each is
self-contained enough to answer part of the question without its neighbors.

### 3. Dense search and keyword search solve different problems.
Dense (embedding) search matches meaning: paraphrases, cross-phrasing, conceptual
questions. Lexical search (BM25, 06) matches exact tokens: error codes, SKUs,
identifiers, rare names — precisely where dense embeddings blur the signal that
matters [I]. Treating them as substitutes instead of complements is the classic
early mistake.
**How to check:** Run your twenty hardest queries through a dense-only and a BM25-only
index and write down which queries each one misses.

### 4. Hybrid retrieval is often stronger than either alone.
Fusing lexical and dense candidate lists covers both failure classes from principle 3,
which is why hybrid retrieval plus a reranker is the workhorse pattern for most
corpora [I]. Reciprocal rank fusion (13) is cheap and training-free. Its arithmetic
deliberately flattens rank magnitude in favor of list agreement: in the constants bank,
a document at ranks {1,3} scores 0.032266 and at {2,1} scores 0.032522 — nearly
identical [E].
**How to check:** Compare recall@k for dense-only, BM25-only, and fused retrieval on
the golden set; if fusion beats neither alone, your corpus is one-sided.

### 5. Retrieval and reranking are different stages (recall vs precision).
The retriever's job is recall: never lose the evidence, cheaply, over the whole
corpus. The reranker's job is precision: reorder a small candidate set so the best
evidence lands in the few prompt slots [I: recall/precision split]. ANN order is not
relevance order; a cross-encoder pass over ~100 candidates typically costs
~200–1000 ms on GPU [I: typical range, not a measurement] and buys exactly the top
slots that enter the prompt (14).
**How to check:** Find queries where the gold chunk was retrieved but ranked below
your prompt cutoff; add a reranker and re-measure MRR/nDCG (45).

### 6. Top-k is not context engineering.
Choosing k and concatenating results in score order is a default, not a context
strategy (03). Which chunks enter the prompt, in what order, deduplicated or
compressed, at what token budget, and with which citation markers is a design layer
of its own (41; ../Context-Engineering/Context-Budget.md). Ten packed chunks of which
four are useful means most of the prompt is noise the model must actively ignore.
**How to check:** Log which packed chunks the answer actually cites or uses — if fewer
than half contribute, the problem is context selection, not k.

### 7. More context is not always better.
Raising k adds cost, latency, and attention dilution before it adds answer quality;
long-context models use evidence unevenly, and relevant text buried mid-context is
under-used [I: the lost-in-the-middle line of work — see
../Context-Engineering/Lost-in-the-Middle-and-Long-Context-Reality.md]. Ten
well-selected chunks routinely beat fifty stuffed ones, at one-fifth the input cost
(principle 14). The question is utilization, not whether the window technically fits.
**How to check:** Sweep k over 5/10/20/50 on the golden set and plot answer quality
and per-request cost together; ship the knee of the curve, not the maximum.

### 8. Metadata is critical in enterprise RAG.
Scoping, freshness, permissions, and tenancy live in metadata, not in embeddings
(12). In an enterprise corpus, "retrieve the right chunk" really means "the right
chunk of the right document, current version, authorized for this user" — that is
metadata and filter engineering (12, 48, 49), and no embedding model can do it [I].
**How to check:** For five real queries, write down the scoping constraints a domain
expert would apply; verify each is enforceable as a pre-search metadata filter.

### 9. RAG must be evaluated at retrieval and generation layers separately.
Retrieval can succeed while generation fails (right chunk present, answer unfaithful)
and vice versa; one end-to-end score cannot tell you which layer to fix (45;
../Evaluation-Engineering/RAG-Evaluation.md). Measure recall/precision at retrieval,
faithfulness and answer relevance at generation, then iterate on the worse layer [I].
**How to check:** Split the golden-set dashboard into retrieval metrics and generation
metrics, and require every shipped change to state which layer it moved.

### 10. Multi-hop questions require more than one-shot retrieval.
"Compare the supplier named in the 2024 contract with the one in the incident
report" needs evidence gathered in sequence: hop one's answer defines hop two's query
(26). One-shot retrieval embeds the whole question once and hopes both evidence sets
appear in top-k [I]. Query decomposition, iterative retrieval, or an agent loop
(24) are the fixes.
**How to check:** Tag golden-set questions by hop count; if multi-hop recall is far
below single-hop recall, add iterative retrieval before you add context.

### 11. Graph retrieval is useful when relationships matter.
When the answer depends on edges — who reports to whom, which part supersedes which,
how entities connect across documents — pairwise chunk similarity is the wrong
primitive (28, 29; ../Graph-Engineering/Knowledge-Graphs-and-GraphRAG.md). Graph
retrieval walks structure; vector retrieval ranks neighbors [I]. The cost is real
extraction and maintenance work, so it must be earned by the failure mix.
**How to check:** Audit failed answers for the class "fact spanned documents linked
by an entity relationship"; if that class is large, prototype graph retrieval on it.

### 12. Agentic RAG helps when retrieval decisions must adapt.
A fixed pipeline cannot decide mid-flight that the first query was wrong, that a
different source is needed, or that the evidence is already sufficient (24; 23).
Agentic RAG treats retrieval as a tool the model invokes under a policy
(24; ../Agents/Tool-Use.md) — more capable, but slower, costlier per request, and
harder to evaluate deterministically [I].
**How to check:** Count requests where the static pipeline failed but a human reading
the intermediate results would clearly have re-queried — that count is the upper
bound on what agentic control could have recovered.

### 13. Security must be enforced before context reaches the model.
Authorization belongs inside the retrieval query as filters, so forbidden documents
never become context (48; 49). Redacting or instructing the model after retrieval is
not a control, because the evidence has already crossed the trust boundary [I].
Retrieved text is untrusted input and must pass the same injection scrutiny as any
external content (../Safety/README.md).
**How to check:** Run retrieval as a low-privilege test principal and verify that zero
high-privilege chunks are returned at the search layer — before any LLM call.

### 14. RAG increases prefill/context cost — budget it from day one.
Every retrieved chunk is input tokens the model must prefill before generating, so
retrieval depth is a per-request cost, not a per-corpus one. Constants-bank
arithmetic at $3/$15 per 1M input/output tokens [E]: 10 chunks × 512 tokens =
5120 input tokens → $0.0153 input + 500 generated tokens → $0.0075 ≈ **$0.023 per
request**; raising to 50 chunks multiplies the input 5× → ≈ **$0.084 per request**.
KV memory scales the same way at ~128 KiB/token for a 70B-class model [E:
../KV-Cache/ convention]: 5120 tokens ≈ **640 MiB**, 25600 tokens ≈ **3200 MiB** —
so the 10→50 chunk jump costs ~2.5 GiB of KV per concurrent slot (43, 44;
../Inference/The-Life-of-a-Token.md).
**How to check:** Multiply your p50 packed-context length by price-per-input-token
and by KV bytes-per-token, and put both numbers on the quality dashboard.

### 15. A simple pipeline that retrieves correctly can beat an overly complex one.
Every added stage — graphs, agents, learned routers, fine-tuned retrievers — buys
capability with latency, cost, and new failure modes (54; 56). A boring hybrid +
rerank pipeline that is measured and tuned usually beats an exotic architecture built
on an unmeasured retriever [I]. Fix the foundational layer first: downstream
complexity amplifies whatever retrieval does, good or bad.
**How to check:** Keep a one-page pipeline diagram where every stage names the metric
that justified it — delete any stage whose metric never moved.

## The pre-mortem checklist
Run this on any RAG system before it ships. Ten questions; every "no" is a known
failure mode (47):

```
 1. Is retrieval recall@k measured separately from answer quality?         (P1, P9)
 2. Are chunks self-contained enough to answer a question fragment?        (P2)
 3. Does the retriever handle exact tokens (IDs, codes) as well as meaning?(P3, P4)
 4. Is there a reranker between the index and the prompt?                  (P5)
 5. Is context selected, ordered, and packed by design — not just top-k?   (P6, P7)
 6. Are access controls enforced as retrieval-time filters?                (P8, P13)
 7. Do multi-hop questions have an iterative retrieval path?               (P10)
 8. Is every pipeline stage justified by a measured metric?                (P15)
 9. Is per-request context cost known at the current k?                    (P14)
10. Can a bad answer be attributed to its failing layer from logs?         (P9, 50)
```

## Key Takeaways
1. Retrieval quality caps generation quality; measure recall before anything else and iterate on the worse layer (45).
2. Chunking, metadata, and ranking are design decisions with measurable trade-offs, not copied settings (10, 12, 14).
3. Hybrid retrieval plus a reranker is the default workhorse; structure (graphs) and agency (agents) must be earned by measurement (13, 28, 24, 54).
4. Context is a budget: the 10→50 chunk jump is ~5× input cost and ~2.5 GiB extra KV per slot [E] (43, 44).
5. Security and tenancy are retrieval-time filters — evidence that should not exist in the prompt must never reach the prompt (48, 49).
